# Prep Time 画面の再設計 — 写真OCRから Grab 注文台帳へ

2026-09-05 / 実測値は本番から取得

## なぜ設計を変えるのか

データ源が変わると**測っているものが変わる**。画面をそのまま残すと、同じ見出しの下に
別の意味の数字が入る。

### 実測比較 — マニラ 2026-09-04（同じ日・同じ店舗）

| 店舗 | 旧（写真OCR） | 新（Grab台帳） | 写真が捉えていた割合 |
|---|---:|---:|---:|
| TAFT | 75件（うち有効46） | **85件** | 88% |
| CUBAO / QC | 21件（うち有効17） | **89件** | **24%** |
| PAR | 23件（うち有効15） | 未取得（セッション切れ） | — |

**Cubao は注文の4分の1しか記録されていなかった。** 旧画面はそれを一度も表示していない。

旧画面の「平均25.7分 / 33.9分」は、注文時刻の36〜50%が誤読なので**そのまま信用できない**
（教訓83）。新しい数字と並べて比較してはいけない。

## 取れるものと取れないもの

Grab の `daily-pagination` が返すのは:

| 取れる | 取れない |
|---|---|
| 注文番号・注文時刻・状態（完了/キャンセル） | **調理完了の絶対時刻** |
| 調理タスクID（全注文に存在） | したがって **所要分数そのもの** |
| Grab の遅延判定（真偽） | |
| 遅延分数 | |

**「何分で作ったか」は出せない。出せるのは「Grabが遅いと判定したか、何分遅れたか」。**
この一点が設計のすべてを決める。0〜100点の採点と S/A/B/C/D/F の等級は、
基になる分数が無いので**成立しない**。

## 新しい指標（実測 2026-09-04・TAFT+QC の174件）

```
遅延率          16.7%  (29/174)
遅延分の中央値   5分     最大 20分
店舗差          TAFT 19%・中央値8分  /  QC 15%・中央値4分
キャンセル      3件（CANCELLED_PASSENGER）
```

時間帯別（マニラ時間）— **山がはっきり出る**:

```
16時 35%   21時 33%   22時 36%      ← 遅れる
12時  0%   14時  0%   19時  0%      ← 遅れない
```

旧画面の「平均◯分」では見えなかった。**1日の中のどこが問題かが分かる**のが実利。

## 画面の構成

### 1. 上部 — 3つの数字だけ

```
注文 174        遅延 29 (16.7%)        中央値 5分
```

「平均所要時間」は廃止。存在しない数字を出さない。

### 2. 時間帯別の帯

遅延率を時間帯で並べる。**ここが唯一「明日から何をするか」に繋がる場所**なので最上段に置く。
16時と21〜22時に人を足すのか、仕込みを前倒すのか、という会話になる。

### 3. 店舗別

TAFT / PAR / CUB の遅延率と中央値。件数も併記する（母数が違えば率は比べられない）。

### 4. 取込の鮮度 — 必ず出す

店舗ごとに**最終取込日**を出す。Grab は1セッション1店舗で、1店舗が止まっても
他の2店舗は入り続けるため、合計だけ見ていると気づけない（教訓89で実際に起きた）。

```
PAR  最終取込 9/5 ✓     TAFT 9/5 ✓     CUB 9/5 ✓
```

止まっていたら赤で日数を出し、`setup-session.js` の実行を促す。

### 5. ドバイ — 「測っていない」と書く

ドバイの旧記録2,270件は**UAEに存在しないGrabFood**の誤読で、根拠が無い。
新方式にドバイの相当物は無い。**空のグラフを出さず、「この都市は現在計測していない」と明記する**
（教訓58 — 見えていない場所について「問題なし」と表示するのが最悪の嘘）。

### 6. 旧データ — 残すが混ぜない

`prep_time_records` 9,910件は削除しない（教訓43）。別タブ「旧方式（〜2026-09）」に置き、
**新しい数字と同じグラフに載せない**。定義が違うので繋げると嘘の傾向線が出る。

## 廃止するもの

**毎朝15〜20件の確認キュー。** 確認する人はOCRと同じ写真を見るので精度は上がらず、
私が2026-07に確認した241件は訂正ゼロだった。Grab の判定は Grab 自身のものなので、
人が承認する余地が無い。**この日課は無くなる。**

写真投稿は残してよいが、**スコアの根拠から外す**。

## 実装の順序

1. `grab_orders` テーブル（注文番号・店舗・注文時刻・状態・遅延真偽・遅延分数）
2. 取込API + `get-orders.js` を3店舗ぶん日次実行（`grab-manila-daily-payout.yml` と同じ枠）
3. **1〜2週間、写真ベースと並走**させて数字を突き合わせる
4. 画面を差し替え、確認キューを外す
