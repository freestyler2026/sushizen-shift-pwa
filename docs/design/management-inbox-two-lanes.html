Inbox を2本に分ける

今すぐ動くものと、翌朝に腰を据えて見るもの。ご提案の設計は実装可能で、 既存のテーブルとテンプレート機構でほぼ収まります。ただし 実データを測った結果、そのままでは効かない箇所が3つありました。 先にそれを書きます。

結論

やる価値があります。ただし閾値を変えてください

Inbox の6割が Product Scoring で埋まっているのは実測どおりです（30日で 546件中327件）。分割は正しい判断です。
緊急レーンは 新設する D を入口にします。現在のFは レシート写真などが混ざっていて使えないというご指摘は、データで裏が取れました —— ただしFの上半分は本物の料理で、それがまさにDにしたいものです。 境目は点数で引けます。

実測

提案を変える3点

1. F は2つの別物が混ざっています

現在の等級は点数の帯だけで決まります（S≧90 / A≧75 / B≧60 / C≧45 / F<45）。 90日のF 937件を点数で割ると、きれいに2つに分かれます。

したがって修正は2つです。①レシート等を等級から外す（not_food）、 ②C と F のあいだに D を作る。

抽出側にクランプはありません（差を取っているだけ）。 つまり Keeta が返している値そのものです。次にやるべきは 注文1件の生JSONを丸ごと出して、他に状態遷移の時刻を持っていないか見ること。 それが1回で済み、あるかないかが確定します。見つかるまでは ドバイの Prep Time レビューは出さないでください。

設計

D を作り、レシートを等級から外す

等級は total_score の帯だけで決まっているので、 帯を1本増やすだけで D は作れます。 採点そのもの（7軸・1〜10点）は変えません。 

S  ≧ 90        A  ≧ 75        B  ≧ 60        C  ≧ 45
D  ≧ 30   ← 新設。「改善が必要な出来の悪いもの」
F  < 30   ← 残り。ほぼ非食品に寄る
Dの下限90日で該当全店1日あたりマニラ1日あたり
40点3804.2約1.4

どれでも緊急レーンに入る量としては適正です。30点を初期値として提案します —— 30〜44点の帯の feedback は全て料理の話（「具が少ない」「盛付が崩れている」）で、 レシートの話は出てこないためです。

ただしこの境目は写真を見て決めるべきものです。 PRODUCT_SCORE_D_MIN を環境変数にして、 デプロイなしで動かせるようにします。運用開始後に 30 / 35 / 40 それぞれの境目付近の写真を10枚ずつ見て、現場の感覚に合わせてください。

レシートは「悪い点数」ではなく「対象外」

採点AIは既に feedback に「これはレシートで食品ではない」と 書いています。言う場所が無いだけです。判定の第1段階に not_food を足し、該当したら7軸の採点自体を行わず、 等級も付けません。 

STEP 1 — Identify the food category:
  "sushi"    …
  "general"  …
  "not_food" … レシート・伝票・POS画面・空の容器・飲料のみ・
               配達バッグのみなど、評価対象の料理が写っていないもの

→ not_food のときは7軸を返さず、grade は付けない（NULL）。
   集計・アラート・支店スコアから完全に除外する。

これで「Fが多い店＝レシートを多く撮っている店」という現在の歪みが 消えます。除外件数は画面に出してください —— 隠すと、撮り方の問題が 見えなくなります。

過去データの扱い

等級の付け直しは安全です。点数は保存済みで変わらず、 ラベルを貼り替えるだけだからです（給与の再計算とは性質が違います）。 バックアップを取ってから一括で再判定してください。

一方 not_food は遡って正確には判定できません —— 7万枚を採点し直すことになります。過去分は total_score ≦ 5 かつ feedback が receipt / no food / invoice に一致 するものだけを対象外に落とし、何件落としたかを報告する形を勧めます。 それ以外は触らない。曖昧なものを推測で消すと、あとで数字の説明がつかなくなります。

設計

レーンは列を1本足すだけ

検知ロジックは一切変えません。変えるのは行き先だけです。 action_templates.lane に既定を持たせ、 management_tasks.lane に実際の行き先を記録します。 

ALTER TABLE action_templates
    ADD COLUMN IF NOT EXISTS lane TEXT NOT NULL DEFAULT 'urgent';
ALTER TABLE management_tasks
    ADD COLUMN IF NOT EXISTS lane TEXT NOT NULL DEFAULT 'urgent';

既定を urgent にしてあるのが要点です。 足した直後の挙動は今日と完全に同じで、テンプレートを1つずつ review に移すことで段階的に切り替わります。 戻すのもテンプレート1行です。

送信から応答までの中央値は Rush Hour Check 未提出 = 223分、 Disposal 未提出 = 196分、Product Score = 123分。 全部が同じ箱にあると、何も緊急になりません。 分割の効果はここに出るはずなので、切替の前後でこの数字を測ってください。 「体感で軽くなった」では、次に増やすときの根拠になりません。

設計

朝のレビューは「1件のタスク」ではありません

16件のタスクを16回閉じる形にすると、いま起きていることの再演になります。 支店×日で1つのオブジェクトにし、最後の Complete Morning Review は1回だけ押します。 

ops_reviews            -- 支店 × 日付 で1行
  city, branch, review_date, status, assigned_to,
  summary        JSONB   -- 生成時点の数字を保存する
  manager_comment TEXT
  completed_by, completed_at, generated_at

ops_review_items       -- 写真1枚 / 遅延1件 で1行
  review_id, kind ('quality' | 'prep_time'),
  source_id,              -- product_score_results.id / aggregator_orders.id
  payload   JSONB,        -- 表示に要る値（等級・写真URL・注文番号・分）
  answer    JSONB,        -- 下記の回答
  answered_by, answered_at

summary を生成時に保存するのが重要です。 毎回その場で数え直す設計にすると、あとで同じレビューを開いたときに数字が 変わります。「9月5日のレビューで見た数字」が再現できなければ、 フィードバックの根拠になりません。

設計

写真1枚あたりの入力を、まず1タップにする

ご提案の4項目（Issue Type / Assessment / Root Cause / Action）を 全件に課すと、16枚 × 4問 = 64回の選択になります。 これは確実に「早く消したい」を再発させます。

実測すると、現在の回答52件のうち 19件（37%）に no_issue が含まれています。 採点しているのはAIなので、Cの相当数は実際には問題がありません。

Step 1（全件・1タップ） この写真は？ [ 問題なし ] → その場で確定。以降の3問は出さない [ 軽微 ] ↓ [ 重大 ] ↓ Step 2（軽微・重大のみ） 何が / なぜ / どうした Issue Type … Presentation / Portion / Cutting / Topping / Packaging / Overcooked / Missing / Wrong / Other Root Cause … Training / Standard / Portion control / Backup / Rush / Ingredient / Other Action Taken … Discord / 個別指導 / 研修 / レシピ確認 / 作り直し / ブリーフィング / HQ報告 / 対応不要 Staff … 複数選択（在籍者から。手入力させない）

「No Issue Found」を Issue Type の選択肢に置かないでください。 それは「何が問題か」の答えではなく「問題ではない」という判断で、階層が違います。 いま同じ欄に混ざっているために no_issue, presentation のような 矛盾した回答が実際に記録されています。

「問題なし」が多いこと自体が情報です

月末に「Cのうち何割が実際には問題なしだったか」を出してください。 その比率が高いままなら、直すべきは店舗ではなく採点の閾値です。 現場に毎朝16枚見せておいて、実は採点が厳しすぎただけ、という状態を 放置しないための数字です。

運用

いつ作り、誰に出すか

  1. 05:00

    現地時刻で前日分を生成

    マニラ 05:00（UTC 21:00）に前日のレビューを作ります。 日付は必ず現地時間で切ってください。 CURRENT_DATE は UTC なので、そのまま使うと マニラの朝8時までが「前日」に入ります。

  2. 担当

    前日の当番から引く

    management_owner_roster が曜日×支店で担当者を持っています。 「前日の曜日」で引けば、ご要望どおり当日の出勤先ではなく 前日の責任店舗になります。既存の表がそのまま使えます。

  3. 出口

    未完了は翌日に持ち越す。消さない

    前日のレビューを完了せずに翌日を迎えたら、2日分が並びます。 自動で期限切れにしないでください。「プライムコストが基準超」と同じで、 昨日の品質問題は今日になっても真です。

    ただし3日以上未完了が続いたら BO Dashboard に出すこと。 誰も見ていないレビューが静かに積み上がるのは、いま Inbox で 起きていることそのものです。
