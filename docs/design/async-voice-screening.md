# §9への回答

## 1. 応募者テーブルの構造と紐づけ方

`hr_applicants`（135件・16列・UUID主キー）

```
id / city / requisition_id / full_name / position_applied / phone / email /
source / referrer_name / status / rejection_reason / notes /
applied_date / created_at / updated_at / assigned_branch
```

音声面接は**別テーブル `hr_voice_screenings`** を作り `applicant_id` で紐づけるのが自然。
`hr_applicants` に列を足さない理由は、1応募者が複数回（別職種・再応募）受けうるため。

⚠️ **`full_name` に表記揺れがある。** `"Gessa Gregorio "`（末尾空白）、`"leomar Go"`（小文字）。
採用14名を在籍名簿と完全一致で照合したら**14名全員が「名簿に無し」**と出た。
正規化して照合すると11名がACTIVE、1名がON_LEAVE、残り3名も表記揺れの疑い。
**音声を人に紐づける以上、保存時に正規化すること。**

## 2. 応募数と無断欠席率

直近8週は週10〜25件で安定。**入口は詰まっていない。**

**無断欠席率 — 測定できない。**

```
面接済み（status='interviewed'）  77名
面接予定（hr_interview_schedules）  3件
面接評価（hr_interview_evaluations） 7件
```

→ **指示の3つの課題のうち「日程調整の往復」と「無断欠席」は、OSに一切記録がない。**
削減効果を後から示せない。指示§5.1が求める「3か月運用してデータで判断」は、
**比較対象が存在しないので現状のままでは成立しない。**

## 4. 文字起こしエンジン

**測らずに選ばない。** 精度は候補者の実際の話し方に依存し、Taglishは各社の公称値が
当てにならない領域なので、**実音声で比較してから決める**ことを提案する。

| | 検証すべき点 |
|---|---|
| OpenAI Whisper (API) | Taglishのコードスイッチ耐性。`language` を指定すると片方に寄る恐れ |
| Deepgram Nova | 多言語モード。フィリピン英語の訛りへの追従 |
| Google STT v2 | 言語自動判定。タガログ対応の有無 |

**比較方法**: 既存スタッフ5名に暫定質問6問を読み上げてもらい（同意のうえ）、
同じ音声を3社に通して**固有名詞（店舗名・料理名）の誤りと、Taglish部分の欠落**を数える。
費用は3社とも1分あたり1円前後で、**月81名×10分でも数千円**。**費用は選定基準にならない。**

⚠️ Phase 2 の前に実施すればよく、**Phase 1 の着手を待たせない。**

## 5. 既存構造と合わない点 — 最重要

### 5-a. 応募フォームが存在しない

指示は「応募フォームの延長として」とあるが、**候補者向けの画面もAPIも1つも無い。**

```
/admin/hr/recruitment          ← HR用。これだけ
POST /api/admin/hr/applicants  ← 認証必須。HRが手入力
```

135件はすべて**HRがMessengerを見ながら手で入力**したもの。
つまり Phase 1 は「録音UIの追加」ではなく、

1. **候補者向けの公開画面**（OSに前例なし）
2. **未認証でアクセスできる経路**（応募者はログインしない）
3. 音声の受け口

の3つを新設することになる。**指示の想定より範囲が広い。**

→ **提案**: 応募フォーム全体を作らず、**音声面接だけの1回限りリンク**にする。
HRが応募者を登録すると、その応募者専用のURL（トークン付き・期限付き）が発行され、
HRがMessengerに貼る。応募の受け口は当面Facebookのままでよい。

### 5-b. 面接記録が9%しか残っていない問題を、音声面接は解決しない

```
面接済み 77名  →  評価記録 7件（9%）
```

記録者は実質1名（Peter Villafuerte）、3件は記録者名が空欄。
**教訓1の「安い道と高い道」がそのまま現存している** — ステータスを1クリックで
`interviewed` に変えれば済み、13項目の評価フォームは省ける。

音声面接を足しても、**要約を読んだ後の「進める／進めない」をどこに残すか**は
同じ問題を抱える。**77件の音声・7件の判断**という同じ形が再現する。

→ **提案**: 要約画面の判断を**1タップ＋理由チップ**にし、**それ自体が記録になる**設計にする。
別フォームを開かせない。指示§4の「HRが自分で判断する」を、記録の残る形で実装する。

### 5-c. 質問セットを切り替える手がかりが実データにない

指示§6は「職種別・店舗別に質問セットを切り替え」を要件としている。しかし

- `position_applied` は**自由記述** — `"L0 kitchen assistant "` `"PIC new QC store "` `"line cook "`
- `requisition_id` が入っているのは **135件中19件（14%）**

**86%の応募者は、どの職種のどの求人に対する応募か機械的に判別できない。**

→ **提案**: Phase 1 で `position_applied` を**選択式**にする（キッチン／キャッシャー／
PIC／ドライバー／BO の5区分程度）。自由記述は備考へ。これは質問セット切替の前提であり、
同時に「求人票あたり何人採れたか」も初めて測れるようになる。

### 5-d. Drive の保存先はサービスアカウントが縛る（教訓30）

`ar_drive.py` の `upload_csv_to_drive()` は `AR_PAYOUTS_FOLDER_ID` 固定・CSV前提。
音声には使えないので**汎用のアップロード関数を足す**。

⚠️ **Driveのファイルは「アップロードしたサービスアカウント」でしか読めない。**
2026-08-27 にレシートで404が出た原因がこれ。音声も**書き込みと読み出しを同じSAに揃える**。

### 5-e. Vercel のリクエスト上限（教訓24）

Next.jsプロキシ経由のリクエストは**約4.3MBで413**になる。
指示§5.3の「1問ごとに分割送信」はこれと整合する。90秒をOpus 24kbpsで録れば
**1問あたり約270KB**なので、分割していれば余裕がある。**まとめて送る設計にしないこと。**

### 5-f. 保持期間の自動削除機構が無い

指示§5.2は「保持期間を設定し自動削除」を求めるが、OSに期限付き削除の仕組みは無い。
worker に日次ジョブを追加する必要がある。**削除は取り消せないので、削除前に
件数をログに出し、実行者名を残す**（教訓54）。

# 実装案

## Phase 1 — 録音と保存（文字起こしなし）

### テーブル

```sql
-- 質問マスタ。コードにハードコードしない（指示§6）
hr_voice_question_sets
  id / name / city / position_group / language / is_active / created_at / created_by
hr_voice_questions
  id / set_id / seq / question_text / limit_seconds / created_at
-- 変更履歴。どの候補者がどのセットを受けたか特定できること（指示§6）
hr_voice_question_set_versions
  id / set_id / version / snapshot_json / created_at / created_by

-- 面接本体
hr_voice_screenings
  id / applicant_id / set_id / set_version / status / token_hash / token_expires_at
  consent_at / consent_text_version / invited_at / started_at / completed_at
  retain_until          -- 自動削除の期限
  decided_by / decided_at / decision / decision_reason   -- 1タップ判断をここに
hr_voice_answers
  id / screening_id / question_id / seq
  drive_file_id / duration_seconds / bytes / uploaded_at
  transcript / transcript_engine / transcribed_at        -- Phase 2 で埋める
  summary / summarised_at                                -- Phase 3 で埋める
```

**`decision` を面接テーブル自身に置く**のが 5-b への答え。別テーブルの別フォームにしない。

### 候補者側の経路

```
POST /api/admin/hr/applicants/{id}/voice-invite   （HR・認証あり）
  → 1回限りのトークンを発行し、URLを返す。HRがMessengerに貼る

GET  /voice/{token}                （候補者・未認証）同意画面 → 録音画面
POST /api/voice/{token}/consent    （候補者・未認証）同意を記録
POST /api/voice/{token}/answer/{seq}（候補者・未認証）1問ずつ音声を送る
```

**未認証の経路はトークンだけが鍵になる。** 以下を必須にする。

- トークンは**候補者1名・1回限り・期限付き**（既定7日）
- DBには**ハッシュのみ**保存
- レート制限（同一トークンで何度も試せない）
- **音声のサイズと形式をサーバー側で検証**（1問5MB上限、audio/webm|ogg|m4a のみ）

### 録音UI

- **音声のみ・動画なし**（指示§5.3）
- `MediaRecorder` + Opus。クライアント側で圧縮
- **1問録れたら即送信**。全問終わってからまとめない
- 途中で切れたら**その問から再開**（送信済みの問はスキップ）
- 各問**録り直し1回まで**（無制限にすると台本を読む練習になり、比較の意味が薄れる）
- 制限時間はマスタの `limit_seconds` に従い、残り時間を表示

### 同意（指示§5.2）

録音開始前に全文を表示し、同意しないと進めない。**同意文のバージョンを保存**する。

> 何を録音するか / 誰が聞くか（HRと採用責任者のみ）/ どこに保存するか /
> **いつ削除するか（不採用の場合◯日後に自動削除）**

### 選択制（指示§5.1）

**音声面接を必須にしない。** 招待画面に2択を置き、**どちらを選んだかを記録**する。

```
○ 今すぐ音声で回答する（所要10分・日程調整不要）
○ 面接日程を調整する
```

⚠️ ただし **5-a のとおり、対面側の日程調整はOSに存在しない**（記録3件）。
比較のためには**対面を選んだ人もOSに記録が残る**必要がある。
Phase 1 で「面接日程を調整する」を選んだ候補者に、
`hr_interview_schedules` の行を作るところまでを含める。**これが無いと Phase 4 が成立しない。**

## Phase 2 — 文字起こし

比較検証（§4）で選んだエンジンに、**Driveの音声を渡してテキスト化**。
worker で非同期処理。**音声そのものはAIに渡さない**（指示§3.4）——
文字起こしエンジンと要約AIを分け、要約には**テキストのみ**を渡す。

## Phase 3 — 要約

**判断ではなく事実の抽出**（指示§4）。プロンプトに以下を明示する。

- 点数・等級・推薦を出さない
- 話し方・訛り・声質に言及しない
- 述べられた事実のみを箇条書きにする

**併せて客観的事実を表示**（判断ではないので可）:
回答時間 / 未回答の問数 / 極端に短い回答 / 候補者自身が入力した希望条件との突合。

⚠️ **要約が指示に反した出力をしたときに気づく手段を置く。**
「Overall」「score」「/10」「recommend」等を含む応答を検知して弾く。
プロンプトだけに頼らない（教訓43 — 例示がそのまま返ってきた前例がある）。

## Phase 4 — 計測

音声／対面の**選択率・完了率・採用到達率**。
Phase 1 で両方の選択を記録していれば成立する。**していなければ何も比較できない。**

# 進め方の提案

**Phase 1 の前に、2つだけ先に片づけることを勧める。**

1. **`position_applied` の選択式化** — 質問セット切替の前提（5-c）
2. **対面面接もOSに記録する** — 比較対象がないと効果を測れない（§2・5-b）

どちらも小さく、Phase 1 と同時に入れられる。**後から足すと、比較したい期間の
データが片側だけ欠ける。**

**本番投入は法務確認後**（指示§10）。実装とテストは並行して進めてよい。
