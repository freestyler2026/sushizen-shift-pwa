いま起きていること

推測ではなく、メニュー定義そのものから確認した5点です。

01 並び順は設計ではなく「作った順」

バックエンドの sort_order は 270 以降が単調増加で、ページを追加するたびに次の番号が振られています。 設計された順序なら起きない 重複した番号が6組あり、これは並びが accretion（堆積）であることの直接の証拠です。

240 HR Today / 240 Payroll　　246 COE / 246 NTE　　282 Spot Purchase / 282 Unworked Shifts　　292 Handbook / 292 HR Policy Docs　　296 AR Payouts / 296 Backup Par Levels　　298 Area Review / 298 People

02 同じ仕事のページが引き離されている

Management Channel の5ページは 60〜66 に並びますが、その間に財務の2ページが割り込んでいます。 お金まわりは 9〜12、37〜43、64〜65、68、71 の5か所に散っています。

60 BO Dashboard → 61 Par Levels → 62 Patterns → 63 People → 64 Vendors → 65 Filing Ledger → 66 Area Manager Review

03 管理ページ5つが「Staff」見出しの下にある

ルートは /admin/* なのに、サイドバーではスタッフ用メニューに混ざっています。 店舗スタッフ向けの項目と管理業務が同じ見出しの下に並んでいる状態です。 初版ではこれを見落としていました（ソースを名前で読み、ルートで確認しなかったため）。

Disposal Report /admin/disposal　Backup Report /admin/backup　Yield Control /admin/yield-control　Daily Inventory /admin/daily-inventory　Travel Path /admin/travel-path

03b Staff と Admin に同じ名前が並ぶ

行き先が違うのに名前が同一で、どちらが自分の用事か画面から判断できません。 カテゴリ分けだけでは解決せず、名前を変える必要があります。

Daily Check ／ Employee Handbook ／ Petty Cash ／ Spot Purchase ／ Transport Expense

04 「Par Levels」が3つある

役割の違う3ページが、ほぼ同じ名前で別々の場所にあります。並べ替えても混乱は残ります。

CK Par Levels /admin/ck/par-levels　Store Par Levels /admin/store-par-levels　Backup Par Levels /admin/management/par-levels

05 メニューと権限台帳が既にずれている

権限台帳にあるのにサイドバーのどこにも無いページが4つ、 逆にサイドバーにあるのにチャンネル未登録が4つあります。 後者は Role Management で制御できないことを意味します（教訓26）。

メニューに無い（URL直打ちのみ）: Attendance（コメントアウト・「Bayzat contract ended」）／ Bayzat Import／Menu Builder／NTE Management
台帳未登録: Role Management ／ Aggregator Price Monitor ／ Yield Control ／ FOCO Investor Portal
前2つは D で判明した 2026-07 に停止した Bayzat 取込に紐づくページで、retire 候補です。

前提として — 利用実績は根拠にできませんでした

どのページが実際に使われているかを api_authz_observations で見ましたが、 ADMIN_AUTHZ_MODE が off のため各1〜2件しか記録がありません。 本提案のカテゴリは業務内容から組んでおり、利用頻度は反映していません。 頻度で並べたい場合は、先に ADMIN_AUTHZ_MODE=log で2週間ほど計測することをお勧めします。

カテゴリだけでは足りない3点

1. 検索欄（最優先）

121項目に対して絞り込み手段がありません。カテゴリを付けても、 目的のページ名を知っている人にとっては9グループを開く手間が増えるだけです。 サイドバー上部に1つ入力欄を置き、名前で絞る。これが単体で一番効きます。

2. 折りたたみと記憶

9カテゴリを全部開いたままでは今と変わりません。既定は折りたたみ、 現在いるページのカテゴリだけ開く。開閉状態は端末に記憶して、毎回開き直さないようにします。

3. 同名ページの改名

問題03・04はカテゴリでは直りません。名前で区別を付ける案です。

構造の提案 — カテゴリを1か所で定義する

いま menu と権限台帳は別々に手で管理されていて、既に4項目ずれています

カテゴリを NavBar.tsx に手で書くと、3つ目の手書きリストが増えるだけです。 access_control.py の各チャンネルに category を持たせ、 既存の scripts/sync-access-channels.py で src/lib/access-channels.ts に生成する形にすれば、 並びと権限が構造的にずれなくなります（教訓26と同じやり方）。

副産物として、問題05の「メニューに無い7ページ / 未登録3ページ」は 生成時に検出できるようになります。

決めていただきたいこと

  1. 9カテゴリの区切りと名前でよいか。特に人事を「名簿・権限」と「採用〜退職」に割るかどうか（合計18項目のため分割案にしています）。
  2. Staff見出しにある管理ページ5つを Admin 側へ移すか。移すと店舗スタッフのメニューからは消えます — 現場が今そこから開いているなら、移動の前に確認が要ります。
  3. メニューに無い4ページをどうするか。Attendance と Bayzat Import は取込元が2026-07で停止しているので retire 候補、Menu Builder と NTE Management は追加候補です。
  4. 台帳未登録の4件（Role Management ほか）をチャンネル登録するか。しないと Role Management から制御できません。
  5. 改名を行うか。現場が今の名前で覚えている場合、混乱と天秤になります。
  6. 利用頻度を先に測るか。ADMIN_AUTHZ_MODE=log を2週間回せば、並び順を実績で決められます（デプロイ不要・無害）。
  7. 実装順。検索欄だけ先に入れる案も有効です（カテゴリ分けより小さく、効果は大きい）。
