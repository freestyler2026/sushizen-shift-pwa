取引先マスタは数日で埋まる

drive_invoices 209件の取引先は 25社のみ。 うち184件が外部仕入、23件が Sushi ZEN 名義の社内振替です。 20社ほど登録すれば207件をカバーします。「マスタが空のまま」にはなりません。

要件社内振替を費用にしてはいけない

取引先マスタの設計で、これだけは初日から必要です。抜けると二重計上が発生します。 

-- drive_invoices の実データ（Dubai）
Sushi ZEN Centrak Kitchen   8件   ← typo。Central の綴り違い
Sushi ZEN Central Kitchen   8件
Sushi ZEN Warehouse         7件
SUNBERRY ... TRADING -     11件   ← 名称が途中で切れている
SUNBERRY ... TRADING L      7件

Sushi ZEN Central Kitchen を「食材費」に分類すると、 CKが外部から仕入れた時点で既に食材費を計上しているため二重になります。 

vendor_master
  vendor_id, canonical_name, name_variants[],
  is_internal          -- Sushi ZEN CK / Warehouse
  default_account_code  -- 社内なら費用科目ではなく振替科目
  default_cost_center, tax_status, tin_or_trn,
  hit_count, last_used_at

name_variants も「将来必要になる」機能ではありません。 typoと切れが、25社しかない段階で既に発生しています。

構造科目・原価センター・配賦先は別の軸

mgmt_overhead の実データを見ると、store_code は 「発生場所」ではなく「どの店が負担するか」として既に使われています。 

-- manila 2026-07
「家賃」    CUB  18,145 / PAR 167,333 / TAFT 278,850   ← 各店の実額
「CK家賃」  CUB  25,000 / PAR  25,000 / TAFT  25,000   ← 25,000×3の均等配賦

store_code に CK・WH・HQ は一度も登場しません。 ここで store_code='CK' にすると配賦情報が消え、月次PLが壊れます。 必要なのは3軸です。

軸例意味既存との関係
account_codeRENT何の費用か59種を統合して新設
cost_centerCK / WH / KD / STAFF_ROOMどこで発生したか新設・CK振替と共有
store_codeCUB / PAR / TAFTどの店が負担するか既存の意味のまま
CK振替との合流点

合流するのは cost_center_master です。drive_invoices ではありません。
Manila のCK納品は ck_deliveries（110件・明細3,490行）に既に構造化されており、 請求書PDFもOCRも介在しません。Manila 側の課題はデータ形式ではなく出庫記録の運用です。
原価センターの定義だけを共通化すれば足ります。別々に作ると必ずずれます。

この段階だけで効く

AIなしでも、費目統一だけで月次PLの精度が上がります。現在は家賃が8行に散っています。日次P&Lの改修とも重なります。

PHASE 1抽出と事実の保存 判断はしない

drive_invoices は列を写すだけ。OCRは残り155件に対してのみ、既存の invoice_ocr_service を流用します。

判断ではなく事実を保存する
保存する（事実）          保存しない（判断）
tin_present: true/false      claimable: 可/不可
receipt_type: OR / SI /
              手書き / 不明

経費性の基準（TIN無しの少額扱い、手書き領収書、Dubai の Simplified Tax Invoice 閾値）は 会計・税務の判断であり、システムが決めるべきではありません。 事実だけ保存しておけば、基準確定後に claimable_rule_version を付けて 過去分も遡って再判定できます。

画面表示も事実だけにします。No TIN found on this receipt. とは書きますが、 This is not claimable. とは書きません。 誤った基準で「経費にならない」と表示すると、スタッフが正しい領収書を捨てかねません。

PHASE 2自動分類と承認画面 新規ページ1つだけ

2回目以降はAIを呼びません。正規化した名前がマスタに当たれば即決定です。 新規取引先のときだけ Claude を使います。

確信度根拠扱い
0.95マスタヒット自動確定・一括承認可
0.85明細から特定（Salmon 2kg）候補提示・1クリック
0.50取引先名だけの推測手動入力

既存の /admin/expense-requests はそのまま残します。 会計データ層の承認は新規ページで行い、既存の承認フローと競合させません。

PHASE 3学習ループ・重複検知・出力 運用しながら精度が上がる
  • 同じ取引先で2回同じ修正が入ったら既定科目を自動更新
  • 重複検知は入り口を跨いで効く（同じレシートが小口と立替の両方に出る等）
  • 会計事務所向けCSV：日付・取引先・TIN/TRN・科目・税抜・税額・税込・原価センター・店舗・画像URL
統合しなかったからこそ効く

5つの入り口を残したまま層で束ねるので、重複検知が入り口を跨いで機能します。統合していたら「同じ表の中の重複」しか見えません。

正直にこの設計でも残るもの

残る問題この設計での扱い
base64画像がDBに直入り（1枚440KB） 層は保存場所を問わないので移行は不要。ただし問題は残る。対象は立替13件（0.33/日）に限られ、緊急性は低い
元行が後から編集・削除される content_hash で検知し差異を表示する。黙って古いまま残さない
どちらが正か 取引の事実は元テーブルが正。会計上の分類は層が正。書き戻さないので競合しない
立替経費の未定着（93名中3名） この設計では解決しない。UIを変えないため。定着は別課題として扱う
