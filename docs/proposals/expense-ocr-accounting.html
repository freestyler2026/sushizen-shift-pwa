Sushi ZEN OS — 実装案 rev.3（税務申告向け）

経理担当の仕訳作業を、確認作業に変える

月に約600枚の請求書とレシートが、すでにシステムに入っています。 読んで、科目を決めて、記帳して、ファイルする——この4工程を置き換える設計です。

2026-08-26 rev.3 · 前版（管理会計向け）から目的を修正

対象経理担当は今、何をしているか

税務申告のためのレシート処理を工程に分けると、置き換えられる範囲がはっきりします。

  1. 収集人
    スタッフからレシートを集める。ここは置き換えられません。紙で回ってくるものは、誰かが撮る必要があります
  2. 読取自動
    日付・取引先・TIN/TRN・税抜額・税額・税込額・明細を読み取る
  3. 科目判断自動 + 確認
    取引先マスタに当たれば即決定。新規のときだけAIが候補を出し、人が承認
  4. 記帳自動
    台帳に1行として確定。手入力は発生しない
  5. ファイリング自動
    画像を恒久保存し、台帳の行から必ず開ける状態にする
  6. 申告人・会計事務所
    科目別集計と仕入税額を出力して渡す。申告そのものは行いません
量の実態

仕入請求書 26.1件/日（Dubai・8日で209件）＋ スタッフのレシート 約3件/日。 合わせて月およそ600枚。1枚2分の手作業なら月20時間です。

前提管理会計とは別の3つの軸が要る

先に作った月次PLの科目マスタは、この用途にはそのままでは使えません。 税務申告には、経営管理では不要な次元が3つあります。

軸管理会計（既存）税務申告（必要）
単位店舗別（CUB / PAR / TAFT …） 法人別。申告は法人ごと。店舗別では申告書が作れません
期間暦月 税務期間。VAT は四半期など、暦月と一致しません
証憑不要 原本が出せること。台帳の行から必ず画像へ辿れる必要があります

さらに、税務では税抜額と税額を分けて持つ必要があります。仕入税額控除は税額の側で計算するためです。 月次PLは税込の総額しか見ていません。

先に作った22科目は無駄になりません

account_master.tax_account_code の列を用意してあります。 レシートを1回分類すれば、税務申告にも月次PLにも使えます。 ただし主従は逆で、税務側の体系が主、月次PLの科目が従です。

訂正既存OCRは税務項目を1つも取っていません

前版で「209件は抽出済みなので再OCR不要」と書きましたが、税務目的では成立しません。 

// invoice_ocr_service.py が現在取っている項目
vendor_name, invoice_number, invoice_date, due_date,
total_amount, currency, line_items, confidence_notes

現在の抽出は発注照合のための項目で、税務のための項目ではありません。 最も価値のある TIN/TRN が、まったく取れていません。

結果として

209件は再抽出が必要です。画像は Drive に残っているので実行可能で、 プロンプトを拡張して1回流すだけです。ただし「タダで使える207件」ではありませんでした。 前版の見積もりを訂正します。

設計既存を触らない方針は維持

5つの入力口はそのまま。参照するだけの台帳を上に載せる構造は前版と同じです。 変わるのは台帳が持つ項目です。 

fin_documents  -- 経費台帳。1行 = 1証憑
  source_table, source_id      -- 元行を指すだけ。書き戻さない
  legal_entity                 -- 申告単位。店舗ではない
  tax_period                   -- 暦月とは別
  doc_date, vendor_id,
  tin_or_trn, receipt_type     -- 事実として保存。判断はしない
  amount_excl_tax, tax_amount, amount_incl_tax, currency,
  tax_account_code, mgmt_account_code, cost_center,
  evidence_url, evidence_hash   -- 原本への恒久リンク
  confidence, review_status,
  locked_at                    -- 申告後は変更不可
  UNIQUE (source_table, source_id)
判断ではなく事実を保存する

tin_or_trn と receipt_type は事実です。 「経費になるか」は判断であり、会計・税務の領域です。 事実だけ保存しておけば、基準が確定した時点で過去分も遡って再判定できます。 基準が変わっても再抽出は不要です。

段階実装の順序

PHASE 1 拡張抽出と台帳 会計事務所を待たない
  • OCRプロンプトに税務項目を追加（tin_or_trn / tax_amount / amount_excl_tax / receipt_type）
  • 既存209件を再抽出。以後は自動
  • スタッフのレシート155件を新規OCR
  • fin_documents に登録。画像への恒久リンクを張る
  • 台帳の一覧・検索・画像表示（科目分類はまだしない）
この段階だけで得られるもの

科目が付いていなくても、「日付・取引先・金額・税額・画像」が一覧で検索できる状態になります。 経理担当の「探す」「読む」「打ち込む」がここで消えます。残るのは科目を決める作業だけです。

PHASE 2 科目の自動分類 会計事務所の体系が要る

ここだけは事務所が決まるまで着手できません。 分類先が存在しないためです。体系が届いたら account_master.tax_account_code に入れます。 

vendor_master
  canonical_name, name_variants[],
  is_internal,              -- Sushi ZEN CK / Warehouse は振替であって費用ではない
  default_tax_account,
  tin_or_trn, tax_status

2回目以降はAIを呼びません。取引先は drive_invoices で 25社のみ。20社ほど登録すれば207件を覆います。数日で埋まります。

社内振替を費用にしない

Sushi ZEN Central Kitchen を食材費に分類すると、 CKが外部から仕入れた時点で計上済みのため二重計上になります。 名寄せの際に is_internal を同時に判定してください。 表記揺れも既に発生しています（Centrak という綴り違いが8件）。

PHASE 3 申告用出力と監査対応 運用が回ってから
  • 期間ロック：申告済み期間は変更不可にする。後から数字が動くと申告と帳簿が食い違います
  • 仕入税額の集計：TIN/TRN あり・なしで分けて出す
  • 重複検知：画像ハッシュと (取引先, 日付, 金額)。入力口を跨いで効きます
  • 監査対応：科目・期間・取引先から絞り込み、その場で原本画像を表示
  • 学習：同じ取引先で2回同じ修正が入ったら既定科目を更新

画面経理担当のための1画面

使う人は店舗マネージャーではなく経理担当です。 1件を丁寧に承認する画面ではなく、100件を一気に流す画面を作ります。

  • 左に証憑画像、右に抽出結果。目線を動かさずに数字を照合できる配置
  • キーボードだけで次へ進める（承認 → 次、修正 → 次）
  • マスタヒットは一括承認。1件ずつ開かない
  • TIN/TRN なしを絞り込める。申告前にまとめて確認するため
  • 期間指定でCSV出力

確認会計事務所に聞くこと

前版から質問の中身が変わります。「体系を共有してほしい」ではなく、実務の受け渡し条件を詰めます。

  • 下処理済みのデータをどの形式で渡せば、そのまま記帳に使えますか。 勘定科目コード・列構成・ファイル形式。記帳工数が下がる分の値引き交渉に直結します
  • 経費性の判定基準。TIN記載なしの少額の扱い、手書き領収書、 Dubai の Simplified Tax Invoice の閾値。これはシステムが決めるべきではありません
  • 証憑の保存要件。電子データで足りるか、紙の原本保管が必要か。保存年数
  • 申告単位。PH法人・UAE法人それぞれの税務期間と申告サイクル
回答を待たずに進められること

Phase 1（拡張抽出・台帳・画像リンク）は全て事務所の回答なしで完了できます。 待つ必要があるのは Phase 2 の分類だけです。
