現状レシートは4つの場所に分かれて入っている

Expense Reimbursement だけを見ていると全体を見誤ります。同じ「スタッフがレシートを上げる」行為が、 4つの別テーブルに、別の形式で入っています。

テーブル件数画像費目取引先
expense_reimbursement_requests13 base64 直入れ6種の英語なし
petty_cash_requests148 photo_url4種（別語彙）なし
transport_expenses18 なしなしなし
receipt_log16 receipt_urldepartment あり + items
ここが分岐点

Expense Reimbursement だけを改修すると、取引先マスタは13件からしか育ちません。 残り182件のレシートは無関係のまま溜まり続けます。 「数か月で8〜9割がマスタヒット」に到達するには、4系統の取り込み口を1つにするのが先です。

逆に言えば、統合さえすれば receipt_log が既に持っている supplier_name と items がそのまま種になります。ゼロからではありません。

前提先に片づけないと機能しない3つ

いずれも「AIの精度」以前の問題です。この3つを飛ばすと、AIが正しく分類しても出力が使えません。

1. 勘定科目マスタが存在しない

「PLの科目をそのまま使えばよい」という方針は正しいのですが、その体系がまだ科目マスタの体を成していません。 mgmt_overhead の費目は59種の自由記述で、既に表記揺れが起きています。

さらに、Expense 側は Ingredients / Transport / Uniform / Equipment / Mobile / Other の6種、 Petty Cash 側は Transportation / Cleaning Supplies / Food & Beverages / Other の4種。 語彙が3つ並立しています。

これを放置するとどうなるか

AIが「食材費」と正しく判定しても、書き込み先が自由記述なら「食材費」「Ingredients」「Food & Beverages」に 分かれて集計できません。科目マスタの整備は、AI導入の前提条件であって、後回しにできる項目ではありません。

段階実装の順序

Phase 1 から価値が出ます。分類（Phase 2）は蓄積が要るので、先に経費性判定を出してください。

PHASE 0 土台 — 科目マスタと画像の置き場 AIなし

この段階だけはAIを使いません。使えるようにするための整地です。

account_master
  account_code      -- 'FOOD', 'UTIL', 'RENT'（固定コード）
  label_en          -- UI表示は英語（CLAUDE.md準拠）
  label_ja          -- 会計事務所への出力用
  pl_group          -- 原価 / 販管費 / 資産計上
  is_active, sort_order
  • 59種の自由記述を、実際に使われている費目へ統合する（家賃8通り → RENT 1つ、店舗は別列）
  • 支出合計 のような合計行を費目から除去
  • Expense / Petty Cash / Overhead の3語彙をこのマスタに寄せる
  • レシート画像を Drive へ。DBは receipt_url のみ保持
この段階だけでも効く

AIを入れなくても、費目が統一されるだけで月次PLの集計精度が上がります。現在は家賃が8行に散っています。

PHASE 1 抽出と経費性判定 OCRのみ・分類なし

科目を当てにいかず、まず構造化して取り出すことと、 経費にならないレシートをその場で弾くことに集中します。 金銭的インパクトが最も大きいのはこちらです。 

// 抽出する項目
vendor_name, receipt_date, currency,
amount_excl_tax, tax_amount, amount_incl_tax,
tin_or_trn, receipt_type, payment_method,
line_items[] { name, qty, amount }
アップロード時点で出す警告

⚠ No TIN on this receipt.
This may not be claimable as a business expense.
Ask the shop for an Official Receipt.

フィリピンは BIR登録の Official Receipt / Sales Invoice で TIN 記載がなければ損金算入も仕入VAT控除もできません。 ドバイも 5%VAT 控除には TRN 記載の Tax Invoice が必要です。
その場で言えば店に戻れます。月末に指摘されても手遅れです。

判定結果は claimable（可 / 不可 / 要確認）として保存し、承認画面で色分けします。 弾くのではなく警告に留めます — 立替の事実は残す必要があるためです。

PHASE 2 取引先マスタと自動分類 中核はAIではない 
vendor_master
  vendor_id, canonical_name, name_variants[],
  default_account_code, default_store_code,
  tax_status, tin_or_trn, country,
  hit_count, last_used_at

2回目以降はAIを呼びません。正規化した名前がマスタに当たれば即決定です。 同じ取引先が常に同じ科目になり、AI費用が下がり、間違いを1回直せば以後ずっと正しくなります。

確信度扱い画面
≥ 0.90自動確定承認待ちに緑で並ぶ
0.60 – 0.90候補提示1クリックで承認、変更も可
< 0.60手動入力科目未設定で表示

マスタヒットは 0.95、明細から特定できた場合は 0.85、 取引先名だけの推測は 0.5 前後を返させます。 「SM Supermarket」だけでは食材か消耗品か決まりませんが、明細に Salmon 2kg があれば食材費で確定します。

画面2ページの具体的な変更

スタッフ側 — /store/expense-request

現在

カテゴリを自分で選ぶ → 金額を打つ → 日付を打つ → レシートは任意

変更後

レシートを撮る → 抽出結果が埋まる → 違うところだけ直す → 送信

  • レシートを必須に。ただし「レシートなし」を理由付きで選べる逃げ道は残す（現金チップ等）
  • 撮影直後にTIN/TRN警告。店を出る前に気づける位置に出すことが要点
  • カテゴリ選択は残すが初期値をAIが埋める。スタッフに科目判断をさせない
  • 店舗は本人の所属店舗を初期値に。変更が必要なときだけ選ばせる
  • 同じレシートの二重申請をその場で検知して知らせる

管理側 — /admin/expense-requests

  • 確信度で3つに分ける。0.90以上は一括承認できるようにする
  • 抽出結果とレシート画像を並べて表示。数字の確認が承認作業の実体です
  • 科目を変更したら classification_feedback に記録（承認者は意識しない）
  • 経費不可のレシートを一覧で抽出できるフィルタ
  • 会計事務所向けCSVを月次で出力
  • 取引先マスタの編集画面（別ページ）— 統合・別名追加・既定科目の変更
承認者の作業を減らすのが目的

100%自動化は目指しません。AIが直接、確定データを作らないのが原則です。 狙いは「1件ずつ科目を考える」から「提示された科目を確認する」への移行です。

交渉会計事務所に聞くこと

選定中であれば、この3点は相見積もりの質問項目に入れる価値があります。

  • この列構成のCSVで受け取れるか。受け取れるなら記帳工数が下がるので、その分の値引き交渉ができます
  • 使用してほしい勘定科目コード体系はあるか。先方の体系に合わせられるなら Phase 0 でそれを採用します
  • 経費性の判定基準に相違はないか。TIN記載の扱い、金額しきい値など

方針やらないこと

やらない理由
AIが確定データを作る必ず人の承認を挟む。誤りが会計データに直接入る経路を作らない
科目を自由記述で持ついま59種で起きている表記揺れを繰り返すだけ
新しい科目体系を作るPLに実在する体系を統合して使う。二重管理にしない
複数店舗の按分をシステムで持つ例外として扱い、按分は会計側で処理するほうが確実
2回目以降もAIを呼ぶマスタ参照で決まる。一貫性が保て、費用も下がる
