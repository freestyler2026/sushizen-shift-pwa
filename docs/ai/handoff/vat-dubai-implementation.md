最終更新 2026-10-23。**案の段階。オーナーの承認後に「現在地」を Phase 0 にして着手する。**

## 進め方（マニラと同じ）

1. 「現在地」の次の未チェック `[ ]` の一番上から着手
2. 1項目ずつ: 実装 → 本番で検証（完了条件を数字で確かめる）→ `[x]` と日付・結果を1行
3. **金額・法令に関わる段階（1・2・3・5）は `/code-review ultra` の対象と申告する**
4. 前提が崩れたら止めて「未決事項」に書き、オーナーに報告する
5. **このOSは FTA に何も提出しない。** 計算・要件チェック・転記表までで、EmaraTax への申告と納付は人が行う

## 現状（2026-10-23 に本番で測った）

### 売上側
| 元データ | 中身 | 状態 |
|---|---|---|
| `pos_revenue_location_daily`（UrbanPiper の店舗別売上） | 5店舗 × 2026-07-01〜10-22 で**114日すべて**揃っている。Q3 は総額 6,451,081 / 割引後 3,027,793 | **最有力の基礎** |
| `pos_sales_daily`（Foodics の注文明細、ブランド別ファイル） | 2025-11〜。**Total Taxes が全行 0** | 税額が入っていない |
| `pos_sales_channel_daily`（プラットフォーム別） | Q3 の SushiZEN が**15日分しか無い** | 欠けているので基礎にしない |
| `ar_payouts`（入金） | Careem・Keeta・Noon・Talabat・Smiles。**入金額だけ**で、手数料・手数料のVAT・割引の負担者は持っていない | 検算用 |

- **全チャネルがデリバリー**（店内飲食のチャネルが無い）。
- **割引が総額の約50%**（Noon はちょうど50%）。割引を誰が負担しているか（店かプラットフォームか）で課税標準が変わる。
- **POS が税額を記録していない。** 税込価格から 5/105 で出すことはできるが、
  **お客さんに渡る領収書（プラットフォームが出すもの）に TRN と VAT が載っているか**は別に確かめる必要がある。

- 請求書の写真・読み取り・承認の流れ（Invoice Inbox）は**ドバイが先に動いていた**ので、材料は揃っている。
- **プラットフォームの手数料の税額票が無い。** 手数料は売上の数十%あり、その 5% は大きな仕入税額になる。今は取り込んでいない。
- 8月中旬より前は請求書の件数が少ない（取り込みが始まった時期）。

### 仕組み
- VAT Ledger の計算（`app/vat_*.py`）は**マニラ専用**。仕入の API は `city != manila` を 422 で断っている。
- 画面・承認・写真・重複判定・自社番号の判定は**都市に依存しない部品が多い**ので流用できる。

- [ ] **0-1 2社の課税期間**（オーナー）: TRN は受領済み（上表）。VAT 登録証で各社の課税期間（開始月）を確認し、DMCC の TRN を `own_tax_numbers` に登録

- [ ] **0-2 今の申告の実績**（オーナー）: 誰が申告しているか、直近の VAT 201 の各箱の金額。台帳の検算に使う

- [x] **0-4 「Charges」の意味**（2026-10-23）: アプリの配達料で課税標準に入れない。アプリ負担の割引は足す（上表）。入金明細での最終確認だけ残る。旧記述: 割引は当店負担で確定（上表）。残る Charges（総額の約6%・割引後から差し引かれている）の中身を書き出しファイルと明細で確定する
- [x] **0-5 お客さんへの税額票**（2026-10-23）: 店舗の領収書は Simplified Tax Invoice・VAT 5% あり。**ただし TRN の先頭1桁欠け、JLT は会社名・TRN が別会社**（上表）。Foodics の領収書設定の修正はオーナー側
- [ ] **0-6 プラットフォームの税額票の取り込み**: Talabat・Careem・Noon・Keeta・Deliveroo・Smiles の手数料の Tax Invoice を、既存のセッションから月次で取る
- [ ] **0-7 リバースチャージの対象**: 海外から買っているサービス（広告・ソフトウェアなど）をドバイの会社が払っているか、支払記録から列挙する
